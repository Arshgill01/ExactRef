## Q-11 — What would have given you a better experience with our CALL-E documentation?

The six sentences the docs owe operators:

1. queued is not idle: a top-level queued can coexist with a live attempt (one live GET did; the Calls table still says only "The call task is queued.").
2. Four words mean done and none is business success: Calls completed is a lifecycle terminal; MCP COMPLETED is run-finished; task_completed is a post-summary judgment; and the 14 Sep changelog now bills a Success fee on "business success criteria" that no API field records.
3. A local timeout is not a hangup and there is no client cancel after accept: docs show timeoutMs 120_000 / timeout_seconds 120, the SDK default is 600 s, and the CLI --timeout-seconds is a 15 s HTTP timeout.
4. Where the summary lives: get_call_run summary / transcript sit under result{}, JSON-RPC response.result is the CallToolResult, and CLI result.structuredContent is the payload; three objects named result.
5. What GET will never show you: call.result_validation_failed is webhook-only; canceled arrives as webhook call.failed (branch on data.status); event type can be call.in_progress while event status stays queued; events page by cursor, goals by after.
6. Retention, concurrency and install: ttl_seconds 0 means keep the number and transcript permanently; the shared pool allows one simultaneous call; the hosted "Install CALL-E for me" guide still teaches npm install -g and bare calle.

One page that uses the same nouns the wire uses. Next to OpenAPI CallStatus, say that queued is not idle: the live Calls table defines it as "The call task is queued," a 2026-09-05 GET stayed queued while an attempt was live, and MCP never says queued (every non-terminal is progress; a client deadline does not cancel the phone call). Put those sentences next to Calls waitForResult (returns on completed / failed / canceled, not on structuredResult) and Goal waitForResult (returns when result or error is non-null); budget several minutes from accept to materialized result (about 4m39s on the one live call); note that docs examples use timeoutMs 120_000 while the SDK default is 600 s and a local timeout does not hang up.

Name the four "done" words so they cannot be substituted: Calls completed is a lifecycle terminal; MCP COMPLETED is run-finished, not task success; task_completed is a post-summary boolean read with completion_confidence and evidence; none of them is an independently verified identifier (calle-docs #44 raised the task_completed naming and #43 the failure_code contradiction; both were closed and the live page on 14 Sep still reads the same way). The live Calls page says CALL-E "validates the structured result against it before returning the terminal call task state" and offers confirmation_code as a required extracted string; calle-docs #40 and #41 (filed by others, open) already report that the terminal state can arrive before the result and that a result can be populated with no evidence, and our one live call is independent evidence for the second: schema-valid plus a confirmed readback is not a write-gate. The 14 Sep changelog adds a fifth word: the Success fee "applies only when the task's defined business success criteria are met" and "a completed conversation alone does not qualify"; the Calls guide's own reservation example (task_completed true, "No table available") is ambiguous under that definition, and nothing on CallTask, CallEvent or the webhook says whether the fee applied. The same entry says the shared number pool supports 1 simultaneous call (purchased numbers 10, SIP unlimited); the Calls guide's wave paragraph still says "dispatch calls in controlled waves" without the number, and no status or error code says "behind the pool limit."

Label the three objects named result: JSON-RPC response.result is the CallToolResult; CLI result.structuredContent is that payload; get_call_run summary / transcript sit under a nested result{} (issue 126). Shipped Cursor 0.1.2 still prints <post_summary or summary or message> at the top level; skills.sh SKILL.md uses that template while its own references/commands.md reads result.summary. PR 129's Time slot reads result.extracted.calling.start / .end; the CLI prints started_at / ended_at. ## Q-13 — Is there any other feedback you'd like to provide?

The Calls API is already enough to build a bounded exception workflow: durable create, poll, small schema, transcript turns. What I still cannot trust for a record write is an exact-character identifier: schema-valid plus readback-yes produced 07198SECTIST for intended 07198FECTIST on the one live English call, and I had to add a write-gate (ExactRef) because no official surface names that state. The agent path does not tell the same story as the SDK path: MCP cannot take result_schema; shipped Cursor 0.1.2 and the skills.sh SKILL.md template read summary at the top level while the MCP handoff and the skills.sh reference file put it under result{}; CLI live verification treats COMPLETED as a pass while the MCP guide says COMPLETED is not task success and ExactRef says neither COMPLETED nor task_completed is writable; calle mcp call exits 0 on isError while calle call status does not. I am not asking for mid-call application tools in v1 (issue 123).

The server already speaks a better contract than its clients read. tools/list carries a typed next_step (poll interval, "ask the user before retrying," "report blocked, do not start another call"), a confirm_expires_at, a retry_confirmation_action input, and a status vocabulary that includes NO ANSWER. Not one shipped client (CLI 0.5.1, five skills, Cursor plugin) reads any of it: they hardcode a 10-second loop and a terminal list spelled NO_ANSWER, forward years-expired plans to run_call, print the confirm_token they are told not to display, and report call_started true before login. The tool descriptions served to those same clients were written for ChatGPT ("wait for the activity card," "the server will notify"), run_call is annotated idempotent, and a 15-second mcp call run_call timeout has no retry_safe so call recover re-submits the confirm pair. GET will not show call.result_validation_failed; calle calls create --wait exits 0 on failed. Offline programmed envelopes are not telephony observations; no second live call was placed after 2026-09-05, and the only 2026-09-14 plan_call runs had no dialable number.
